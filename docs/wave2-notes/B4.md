# B4 — collectors and enrichment adapters

Notes for the orchestrator. Nothing here needs action to make the suite pass; the
items marked **ACTION** affect other work packages.

## Dependencies

* **`httpx` is not in the pinned set and was not added.** The two network adapters
  import an HTTP client *inside the call* (`enrichment/providers/__init__.http_json`),
  preferring `httpx` when present and falling back to `urllib.request`. Both modules
  therefore import cleanly with no HTTP library, no credentials and no network,
  which is what lets the compliance tests instantiate every shipped adapter
  offline. No change to `pyproject.toml` is required.
* **`ijson` is not available, so the HAR parser is not streaming.** R4 asked for
  `log.entries` to be streamed because session HARs routinely exceed 100 MB;
  `har.py` uses `json.loads` over the whole document instead. Correctness is
  unaffected and traversal is bounded (`_MAX_WALK_NODES`, `_MAX_WALK_DEPTH`), but
  peak memory is roughly the file size. If large-HAR support matters, add `ijson`
  and the entry loop can be swapped without touching the extraction code.

## Deviations from the research docs, and why

| Deviation | Reason |
|---|---|
| R2's `CompliancePosture` dataclass is named `ProviderCompliance`; R2's `Provenance` is `EnrichmentProvenance`. | `core/models.py` is frozen and already owns both names. `EnrichmentProvenance.to_core()` converts. |
| R4's six-value posture enum is not implemented; `core.models.CompliancePosture` is used. | Setup guide §4 (B4) specifies the frozen four-value enum. Mapping: `first_party` → `FIRST_PARTY_EXPORT`; `passive_capture` and `manual` → `MANUAL_CAPTURE`; `inference` is carried as `CaptureStatus.SKIPPED_BY_DEGREE`, not as a posture; `active_browser`/`automated` collapse into `AUTOMATED`, which no collector declares and `registry.register()` refuses. |
| `LookupKey.cache_id()` is implemented in `enrichment/interface.py` rather than `normalize.py`. | `normalize` imports `interface`; putting it the other way round is an import cycle. It is pure stdlib hashing and is re-exported as `normalize.cache_id`. |
| R4's separate `VoyagerJsonlCollector`, `MutualsJsonlCollector` and `DegreePruneCollector` are not separate modules. | File ownership was scoped to `manual_csv.py` and `har.py`. Degree pruning is folded into `manual_csv.read_targets`, which emits `skipped_by_degree` captures for 3rd/out-of-network targets, labelled as inference. The other two are straightforward additions later. |
| R2's `enrichment/discovery/` subpackage (Tavily, Exa) was not built. | Not in the owned file list. |
| Rule V13 (unrestricted `connectionOf` capture) is severity `error` and rejects the **record**, not the file. | R4 labels it fatal. A HAR is a whole browsing session; one stray request — possibly issued by LinkedIn's own UI — should not discard 100 good captures. The substantive requirement (the record is rejected, no edges taken) is honoured. |

## Rule V8 without ever naming the credential

R4's V8 says to reject any input containing `li_at=`, `JSESSIONID` or a
`csrf-token` header. The setup guide and this work package say more strongly that
**no code path in the package may reference `li_at`**. Those pull in opposite
directions, since the literal scan needs the literal.

Resolved by refusing *structurally* instead: `har.py` never reads a header or
cookie container for content, and refuses the whole file (`HAR_UNSANITISED`,
fatal) when any entry carries a populated `cookies` array or a header named
`cookie` / `set-cookie` / `authorization` / `csrf-token` — generic HTTP
vocabulary, declared in `schemas.py` under `har.sensitive_header_names`. The
package therefore contains no LinkedIn credential identifier at all, and
`tests/test_collect_guardrails.py` asserts it across every `.py` file in
`src/interlayer/` (the token is assembled from fragments in the test so the guard
file is not itself a match). If a repository-wide grep for `li_at` is added later,
it will be clean.

## ACTION — config interaction with PRIV-04

`Config.enabled_adapters` defaults to `["first_party_export"]`, which maps to
`{CompliancePosture.FIRST_PARTY_EXPORT}`. **Both shipped collectors declare
`MANUAL_CAPTURE`**, so with the default config `registry.for_posture(...)` returns
nothing and no HAR or hand-filled CSV is read. That is the correct reading of
PRIV-04, but it means the edge collectors are off until the user adds
`manual_capture` to `enabled_adapters`.

`registry.load_all` now emits a single explicit `posture.not_allowed` diagnostic in
that state ("nothing was read — this is a configuration state, not an empty
network") with the remedy naming the posture to add. **B5's CLI should surface that
diagnostic prominently**, and the runbook should say plainly that collecting edges
requires enabling `manual_capture`. Otherwise the default install looks like a tool
that finds no bridges.

`registry.DEFAULT_ALLOWED_POSTURES` (`first_party_export` + `manual_capture`) is
only the default argument for direct API use; the CLI should pass
`config.enabled_postures()` and let the diagnostic do its work.

## Cross-package imports

Beyond `core.models` and `core.ids`, both packages now import `core.errors`
(written by B1 after this package was scoped). `CollectorError` extends
`CollectError`; `CompliancePostureError` extends both `CollectorError` and
`ComplianceError`; `ProviderError` extends `InterlayerError` and
`ProviderDisabledError` also extends `ComplianceError`; `BudgetExceeded` extends
`InterlayerError`. `core/errors.py` documents `CollectError` as "owned by
`interlayer.collect`" and says `collect/` raises `ComplianceError` for a
non-enabled posture, so this is the intended coupling — flagged only because the
original brief named `models` and `ids` alone.

## `schemas.py` — what `verified` means

`verified=True` means "this project has confirmed the shape against an artefact it
can actually see". That is true of the 16 HAR-container entries (an open format,
independent of LinkedIn, exercised by the fixtures) and the 9 CSV column-spec
entries (this project owns them). It is false for **all 37 LinkedIn-specific
entries**, without exception, because the egress policy blocked `linkedin.com` and
no agent here ever saw a real response. Flipping one to `True` is a claim that a
human compared it against a captured artefact — not that the parser worked once.

Every unverified entry carries a `Confidence` (`medium` where R4 quoted source code
or an issue thread verbatim, `low` where it quoted prose) and a `source` citation.
`schemas.unverified_keys()` and `schemas.table_report()` are available for the CLI
to print, and `schemas.STALENESS_WARNING` is the sentence any shipped document
should quote.
