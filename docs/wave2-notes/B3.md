## 1. Discrepancy — R3 §T5.3 cannot be satisfied on the fixture it names

**What R3 specifies.**

> **T5.3** Dropping 30% / 60% / 80% of target columns from the T4 base fixture
> keeps `NMI >= 0.80 / 0.70 / 0.70` on members retaining ≥1 edge
> (observed 0.861 / 0.797 / 0.759).

**The problem.** The T4 base fixture is defined in §T4 as *"6 planted pockets
(12 targets, 25 members each, 12% cross-pocket noise, `default_rng(3)`)"* — that
is, **12 target columns total**. Dropping 80% of 12 columns leaves 2. Two binary
columns cannot encode six pockets: the projection collapses to at most three
distinguishable member groups regardless of the algorithm. This is an
information-theoretic property of the fixture, not a defect in Leiden, RA
weighting, or this implementation.

**Measured, on the fixture as specified** (`tests/test_graph_fixtures.py::hub_fixture`
with `with_hub=False`, columns dropped by marking `harvested=False`, `default_rng(11)`):

| drop | surviving columns | bridges | k found | NMI | R3 published |
|---|---|---|---|---|---|
| 0%  | 12 | 150 | 6 | **1.0000** | — |
| 30% |  8 | 126 | 5 | **0.9897** | 0.861 |
| 60% |  5 | 102 | 4 | **0.9708** | 0.797 |
| 80% |  2 |  26 | 1 | **0.0000** | 0.759 |

**Why the published numbers must come from a different fixture.** R3's own §1
summary reports the missing-data curve as part of the projection-vs-bipartite-CPM
head-to-head: *"NMI 0.885 vs 0.887 at full data; 0.759 vs 0.746 at 80% loss"*. The
full-data NMI of that fixture is **0.885**. The T4 base fixture's full-data NMI is
**1.0000** (measured above, and §T4.4 separately reports 0.887 *with* the hub
present). A fixture cannot have full-data NMI of both 0.885 and 1.0000, so §T5.3's
observed values were measured on the head-to-head instance — most plausibly the
"noisier 320-member instance" with k=8 referenced in R3 §2.3 — and the phrase
"the T4 base fixture" in the test spec is a drafting error.

Note also that the 80% figure (0.759) is *higher* than the 60% figure (0.797) is
low — the published curve is monotone and gentle, which is impossible on a
2-surviving-column graph.

**What was built instead.** `tests/test_graph_missing.py` implements T5.3 three ways:

1. `test_t5_3_degradation_is_graceful` — the structural assertion R3 intends
   (`NMI >= 0.80 / 0.70 / 0.70` at 30/60/80% loss) on a 320-member / 8-pocket /
   64-target instance, which has enough columns for the 80% case to be meaningful.
   Passes at 1.000 / 0.990 / 0.935.
2. `test_t5_3_t4_base_fixture_degradation` — the same floors on R3's *named*
   fixture, for the two loss levels it can support (30% and 60%). Passes.
3. `test_t5_3_twelve_column_fixture_cannot_survive_eighty_percent_loss` — asserts
   the collapse explicitly (`k <= 3`, `NMI < 0.70`, ≤3 surviving columns), so the
   reason case 1 uses a different fixture is itself under test rather than being a
   silent substitution.

**No action needed from the orchestrator** unless R3's numbers are to be
re-derived; the acceptance floors are met and the limitation is pinned by a test.

## 2. Ambiguities resolved, recorded so nobody re-derives them

### 2.1 T1.5 modularity 0.260000 is the *unweighted* value

Clustering runs on the weighted RA projection, so the natural expectation is a
weighted modularity. It is not what R3 published. Measured on the golden fixture
for the T1.5 partition:

| convention | value |
|---|---|
| `g.modularity(membership)` — igraph, unweighted | **0.260000** ← R3's value |
| `g.modularity(membership, weights="weight")` | 0.447066 |
| `leidenalg` `partition.modularity` | 0.260000 |

`graph/cluster.py::modularity` therefore computes the unweighted value, and the
docstring says why. Both R3-consistent conventions agree, so this is settled, not
a judgement call — but a future reader changing it to weighted would break T1.5.

### 2.2 T2.5 "same partition" means same blocks, not same labels

R3 §T2.5 asks that `leiden_consensus(base_seed=42)` and `base_seed=1000` give the
same partition on T1. They give the same **blocks** with different integer labels:

```
base_seed=42   -> {m0,m1,m2}:1  {m3,m4,m5}:2  {m6,m7,m8}:0
base_seed=1000 -> {m0,m1,m2}:0  {m3,m4,m5}:2  {m6,m7,m8}:1
```

leidenalg numbers communities by discovery order, which the seed block moves.
`ConsensusPartition.blocks()` exists for this comparison. The default
`base_seed=42` path reproduces R3's published label vector
`{m0:1, m1:1, m2:1, m3:2, m4:2, m5:2, m6:0, m7:0, m8:0}` **exactly**, under both
`leiden_once` and the full 25-seed consensus, so the fingerprint is stable.

### 2.3 T4 fixture reconstruction is under-determined but its golden values are not

R3 §T4 does not state how the 12% cross-pocket noise is applied or how the 12
targets divide among 6 pockets. The reconstruction in `hub_fixture` (2 targets per
pocket; 12% chance per member of one extra edge to a uniformly random target)
reproduces all three published weights **exactly**:

| assertion | R3 | measured |
|---|---|---|
| T4.1 raw count, hub-only pair | 1.0 | **1.0** |
| T4.2 RA, same pair | 0.0100 | **0.0100** |
| T4.3 AA, same pair | ≈0.2171 | **0.21714724** |

These are the load-bearing values and they depend only on the hub having degree
exactly 100 and the pair sharing nothing else — which the reconstruction achieves.
T4.4 asserts `k == 6, NMI >= 0.85`; measured **NMI 1.0000** against R3's observed
0.887, i.e. this reconstruction's noise is gentler than R3's. The assertion holds
with margin; the absolute value is not a golden number in R3's spec.

### 2.4 The `" | "` sentinel alone does **not** fix the bigram-straddle bug

Worth flagging because R3 §6 presents the sentinel join as the fix. It is not
sufficient. sklearn's default `token_pattern` discards `|` as a non-word
character, so the bigram window closes straight over the join and the straddle
happens silently — verified: with a plain sentinel join the vocabulary still
contains `infra google` and `2016 beta`.

`graph/label.py` therefore uses a **field-aware analyzer** that tokenises each
field separately and emits bigrams only within a field (R3's stated alternative,
"build separate per-field vectorizers and merge", in one pass). T7.1's expected
labels — `google`, `wharton`, `nyc` — are unaffected. T7.3 asserts every emitted
bigram is reproducible from a single attribute field of a single member.

## 3. Implementation decisions worth knowing

- **Consensus has a dense-matrix guard.** The co-association matrix is dense
  `|B|²`; at 8,000 bridges that is 128 MB even as `uint16`. Above
  `DEFAULT_MAX_CONSENSUS_NODES = 5000` the pipeline falls back to single-seed
  Leiden, which remains fully deterministic (the sort, not the seed, is what
  guarantees that) but loses the consensus averaging and the per-node stability
  surface. `params["consensus_applied"]` records which path ran. R3's T9.1 measures
  plain Leiden at 8,000 nodes, not consensus, so this does not weaken any test.
- **Harvested targets with zero mutuals are kept as zero columns** of `A`, so the
  `max(d_t, 1)` guard is genuinely exercised rather than being dead code. They are
  a real observation ("we looked and found nobody"), distinct from unharvested.
- **`min_confidence` gates inferred edges only.** Observed edges carry
  `confidence = 1.0` by contract; dropping an actual observation because a field
  was mis-populated would be a worse failure than keeping it. Tested.
- **`AnalysisResult.fingerprint` is the canonical-result digest**, not R3's
  membership-only digest — the setup guide §3 rule 6 asks for "SHA-256 over the
  canonical result", which is strictly stronger. R3's exact definition is still
  available as `fingerprint.membership_fingerprint()` and is tested separately.
- **`reach`/`rarity` always come from the unweighted bipartite graph**, even when
  `use_confidence=True` weights the projection, so an inferred-edges run cannot
  restate someone's reach as a fraction.

## 4. Contract feedback

None. `core/models.py` and `core/ids.py` carried everything the graph engine
needed; `Brokerage`, `Cluster`, `Coverage`, `NextTarget` and `AnalysisResult` were
populated without a single workaround, and `ids.edge_key` was used for the T8.5
dedupe as intended.

One observation for whoever writes the report layer: `Member` carries
`company_raw` and `position` but not school or city, which R3's labelling section
assumes. `label_clusters` therefore takes an `attributes:` callable (defaulting to
company + title) so a caller with richer data can supply it without the model
changing. This is a note, not a request — the omission is correct under the
PRIV-08 field allowlist.
